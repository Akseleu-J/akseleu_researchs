# GDN-3 — текущий статус аудита

**Дата аудита:** 9 октября 2026 г.  
**Что проверено:** рабочий пакет `gdn3_kit/gdn3_kit` и состав приложенного `gdn3_full (1).zip`; код прочитан выборочно по основным путям (конфигурация, mixer, cache/read/router, README/DESIGN, runner). Тесты и обучение в этой сессии не запускались. Выводы из ноутбуков и предыдущих заметок ниже помечены как сохранённые результаты, а не повторные запуски.

## Короткий статус

- **M1 / преимущество памяти: OPEN, не доказано.** Короткий MQAR (L=512) из прежнего аудита показывает, что baseline GDN-2c уже решает задачу, а hybrid почти не добавляет качества. Длинные эксперименты либо невалидны/несопоставимы, либо не проходят health check. Нет завершённого парного capacity-сравнения с общим протоколом, несколькими seed и iso-state.
- **Базовая реализация `gdn3_kit`:** содержательная исследовательская реализация с serial и Pallas backend, режимами `gdn2/local/hybrid/snap`, потоковым cache и бенчмарками. Текущий локальный checkout не подтверждён запуском в этом аудите. Ноутбучные PASS относятся к конкретному сохранённому снимку, не автоматически к этой папке.
- **`gdn3_full` в ZIP:** это отдельная реконструкция с иным набором файлов и новыми модулями (Fenwick, archive, ops и др.). Она не является обновлением `gdn3_kit` и не имеет доказанной байтовой или тестовой совместимости с ним. Изменения из `gdn3_full/docs/STATUS.md` следует считать заявленными для ZIP-снимка, пока не установлены его точный commit, зависимости и повторяемые тесты.
- **Результат проекта в целом:** есть основание продолжать функциональную reference-валидацию, но центральная гипотеза о приросте capacity пока не проверена корректно. Нельзя заявлять, что GDN-3 уже лучше GDN-2 или что Pallas-путь текущего checkout сертифицирован.

## Что не так / основные риски

1. **Снимки разошлись.** `gdn3_kit` в рабочей папке и `gdn3_full` в ZIP имеют различную структуру и набор модулей. В ZIP заявлены `fenwick.py`, `ops.py`, `archive.py`, `test_fenwick.py`, `test_pallas.py`; в рабочем kit вместо этого видны `cache.py`, `segments.py`, `read.py`, один `test_gdn3.py` и runner. Статусы из ZIP нельзя переносить на kit и наоборот.
2. **Нет актуального воспроизведения M0.** README kit всё ещё говорит, что TPU/JAX-проверки не запускались в исходной среде, а сохранённый поздний Pallas PASS относится к ноутбучному снимку. Текущая версия, backend, JAX/Pallas и `atomic_gdn2` не закреплены одной воспроизводимой записью.
3. **M1 невалиден как доказательство выигрыша.** L=512 насыщает baseline; старые длинные прогоны смешивают позиции запросов, параметры обучения и здоровье ветвей. Нет финального парного набора GDN-2c / hybrid learned / oracle на одном каноническом генераторе, трёх seed, заранее заданном пороге и iso-state.
4. **Oracle — версионно-зависимо.** Старый аудит kit описывал oracle как отсутствующий/прокси. В ZIP-заметке позднее заявлен `oracle_weights` только для parallel engine, fixed seg и кратных длин, с непрогнанными JAX-тестами. Сначала определить целевую ветку и проверить реализацию, иначе диагностика роутера ненадёжна.
5. **Fenwick и CCQ не следует считать закрытыми для kit.** В ZIP-заметке Fenwick заявлен как отдельный модуль с NumPy-проверкой, но не подключён к роутеру; CCQ по paper помечен как не реализованный из-за несовпадающей ковариации. В kit дизайн прямо относит log-linear/Fenwick к будущему этапу. Это не блокирует базовый M1.
6. **SSE по paper не завершён.** В ZIP-аудите уточнено, что `sse_topk_rows`/`sse_k` — другая операция, чем row-sparse запись из статьи; партиционирование и balance loss не подтверждены доступным текстом. Не считать вставленный план спецификацией реализации без первоисточника.
7. **Есть устаревшие заявления в документации.** Kit README обещает любой `L` с автоматическим паддингом, но `mixer_fwd` требует, чтобы `L % cfg.align(be.bt) == 0`, и выбрасывает ошибку вместо паддинга. Проверить фактический pad/crop в верхнем `model.forward` и привести README/DESIGN к поведению. Также дизайн пишет «decode O(1)», хотя archive route/read в `step_read` сравнивает query со всеми `N` банками: точнее описывать отдельно постоянный recurrent update и O(N·D·m + k·D²) archive retrieval.
8. **Конфигурационный риск.** В kit `seg` по умолчанию 512, тогда как дизайн рекомендует начинать с 128 для D=128 в MQAR capacity. Это допустимый дефолт для иных задач, но для M1 он может перегружать банки и скрывать эффект. `arch_heads=0` означает «все головы» для архивных режимов, а не ноль архивных голов; это задокументировано в property, но легко ошибиться при чтении CLI.
9. **Показатели скорости/LM отсутствуют как финальные результаты.** Наличие `speed.py` и `lm_position.py` не заменяет измерения с закреплённым устройством, версией ядра, warmup и синхронизацией.

## Куда копать — по порядку

### 1. Зафиксировать, какая ветка каноническая

- Для продолжения базового эксперимента считать `gdn3_kit` канонической исходной реализацией, как предлагает заметка в ZIP.
- Сохранить hash/архив именно этого состояния и отдельно хранить `gdn3_full`; не переносить патчи пакетом.
- Составить краткий diff-инвентарь ZIP↔kit. Переносить только нужные идеи по одной, с тестом эквивалентности `gate=0 → GDN-2`.

### 2. Закрыть M0-reference на текущем kit

- На среде с совместимым JAX запустить `python tests/run.py --backend serial` и сохранить полный лог, hash исходников и версии Python/JAX.
- Проверить ключевые свойства: hybrid gate=0 против GDN-2; причинность на границе/внутри сегмента; decode против parallel/prefill для неполного хвоста; fifo/merge; finite gradients.
- До Pallas зафиксировать точную функцию padding/cropping для произвольного L и исправить расхождение кода с README/DESIGN.

### 3. Закрепить один честный MQAR-протокол

- Один генератор и один eval путь для GDN-2c, hybrid-learned и oracle. Зафиксировать непересекающиеся диапазоны key/value/filler, порядок `[facts][filler][queries]`, явные `L`, `qstart`, `P`, `n_q`, batch, seeds, число supervised токенов, optimizer/lr/warmup, decay, dtype и eval samples.
- Добавить детерминированную проверку генератора: targets ссылаются на существующие факты, query после фактов, нет пересечения диапазонов, длина не обрезает запросы.
- Сначала воспроизвести короткий positive control. Затем подобрать длинную задачу, которую baseline действительно обучает. Если baseline не здоров, capacity-сравнение не интерпретировать.

### 4. Провести M1 как парный эксперимент

- На той же задаче сравнить GDN-2c / hybrid learned / oracle; oracle использовать только для диагностики.
- Заранее задать P* (например accuracy ≥0.9), критерий здоровья, остановку при blow-up и критерий успеха из DESIGN (`P*(hybrid) ≥ 2×P*(GDN-2)` и статистически убедительный gap).
- Записать loss/accuracy кривые, gate, router entropy/выбранные банки, grad norm, skipped updates и runtime. После первого сигнала повторить минимум на 3 seed, затем выполнить iso-state контроль.

### 5. Вернуть Pallas только после serial parity

- Сопоставить точный Pallas checkout/`atomic_gdn2` с сохранёнными notebook PASS.
- На зафиксированных inputs/weights сравнить logits и градиенты serial↔Pallas до тренировки. Отдельно разрешить крупное расхождение из `5_10_3matrix` для соответствующего snapshot/config.
- Затем выполнить Pallas runner и измерения скорости. M0-Pallas и M2/M3 оставить отдельными статусами от M1.

### 6. Только потом переносить расширения из ZIP

Приоритет расширений после базовой валидации: (а) корректный oracle; (б) Fenwick, если нужен быстрый range/recency доступ — при этом отдельно решить интеграцию с чтением; (в) SSE после фиксации текста §3.2/§3.3; (г) CCQ только по точной covariance ключей и параметризации первоисточника. Не начинать с адаптивной сегментации или нескольких новых модификаций одновременно.

### Формулировка статуса для журнала

> **M1: открыт, не подтверждён.** Сохранённые результаты поддерживают продолжение reference-валидации, но короткий MQAR уже решает GDN-2c, а длинные эксперименты пока не образуют здоровое парное capacity-сравнение. Kit и приложенный `gdn3_full` — разные снимки. Следующий шаг — закрепить kit, закрыть M0-reference, затем запустить единый MQAR health control и парный GDN-2c/hybrid/oracle; после первичного сигнала — 3 seed и iso-state. Pallas и расширения из ZIP оценивать отдельно.
